1. The Name — Plinth

1.1 Etymology

The word plinth comes from the Greek plinthos and Latin plinthus — meaning a flat slab or brick. In classical architecture, the plinth is the lowest, widest part of a column base. It makes contact with the ground, distributes the load, and anchors everything above it. It is not the most visible part of a building. It is often overlooked. But without it, nothing stands straight.

1.2 Why This Name for a Design System

This design system was built with a specific purpose: to serve as the foundation from which other design systems can be created. Not just a collection of components, but a base layer — tokens, structure, naming conventions, and component architecture — that a designer or engineer can take and re-theme into an entirely new brand identity by changing a handful of values. That is exactly what a plinth does architecturally.

1.3 The Design Engineer Perspective

Naming a design system is an act of infrastructure thinking. It signals intent to every person who will use it — designers, engineers, product managers — and it sets expectations about how the system should be treated. A name like Plinth says: this is not a pretty collection of buttons. This is the structural layer your product sits on. It demands care, precision, and respect for the people who will build on top of it.

Plinth operates at the intersection of visual design and frontend engineering. Every decision — from the three-layer token architecture to the variant-complete component states — is made with both the Figma canvas and the code editor in mind. The system is infrastructure, not decoration. Infrastructure with craft.

"The plinth is the base everything stands on. Remove it and the structure loses its footing."

2. The Problem Plinth Solves

2.1 The Rebranding Problem

Most design systems are built for one brand. Everything — colors, typography, spacing, component styles — is hardcoded in terms of that single brand identity. When a company rebrands, the work starts from scratch. Colors are changed manually across hundreds of components. Design files are updated piece by piece. Engineers search through codebases replacing hex values. The process takes months and introduces inconsistency at every step.

NOTEPlinth's three-collection token architecture — Primitives → Semantic → Component — means that a full rebrand requires changing fewer than 10 token values. Every component updates automatically.

2.2 The Design-to-Code Gap

The gap between Figma and code is a persistent source of friction in product development. When tokens are not shared between design and engineering, developers interpret designs and make their own decisions. Drift accumulates. The button in the design file is not exactly the button in the browser. Over time, small discrepancies compound into visible inconsistency, eroding trust between designers and engineers and degrading the user experience.

Plinth closes this gap by making the token structure identical in Figma Variables and in a JSON token file that maps directly to CSS custom properties. What you see in Figma is what you get in code. No interpretation layer. No drift.

2.3 The Inconsistency Problem

Without a system, individual decisions compound into visual inconsistency across a product over time. One designer uses a 12px corner radius. Another uses 8px. One engineer picks #4F46E5 for a primary action. Another picks #4338CA because it looked better in context. These are not malicious decisions — they are the natural result of working without shared constraints.

Plinth makes the right decision the easy decision. Token names encode intent. Component variants cover every state. Consistency is the default, not the exception.

3. Design Principles

These are not aesthetic preferences. They are structural decisions. Every component, token, and pattern in Plinth exists because it was required by one or more of these principles. If something in the system does not satisfy at least one principle, it does not belong.

01

Token-First

Every visual decision traces back to a named token. No raw hex values, no hardcoded pixel numbers without token references in components.

02

Minimal by Default

No decorative opinions. No gradients. No shadows beyond functional elevation. The minimal base is the easiest to theme.

03

Variant-Complete

Every interactive state is modelled: hover, active, focus, disabled, loading, error. Nothing is left to interpretation.

04

Composable

Atomic hierarchy — Atoms → Molecules → Organisms. Nothing built in isolation from the system.

05

Theme-Ready

The entire system re-themes by changing six color token values. Six values. One new identity.

"Six token changes. One entirely new brand identity."

4. System Architecture

4.1 The Three Token Layers

Plinth's architecture is built around three token collections, each with a distinct purpose and strict rules about what can reference it. This separation is what makes re-theming possible without touching a single component.

Component Layer
Component-scoped tokens. Decouples components from global semantic changes.
Layer 3
Semantic Layer
Meaning-driven aliases. Has Light and Dark modes. Edit this layer to re-theme.
Layer 2
Primitives Layer
Raw values only. Hex codes, px numbers. Never referenced directly by components.
Layer 1

4.2 How Re-Theming Works

The chain of references is explicit, traceable, and designed to be changed at a single point:

  • 1 Button fill → references Component/button/bg/solid
  • 2 Component/button/bg/solid → references Semantic/color/primary
  • 3 Semantic/color/primary → references Primitives/color/brand/500
  • 4 Primitives/color/brand/500 → holds the raw hex value #4F46E5

To re-theme, only step 3 changes. The Semantic layer remaps to a different primitive, and every component updates instantly.

7.2 Optional Brand Adjustments

  • Corner radius — change radius/md and radius/lg for sharper or rounder brands
  • Typography — swap font family if brand has a custom typeface
  • Neutral scale — remap neutral primitives for dark or coloured neutral palettes
  • Shadow tokens — adjust elevation tokens for flatter or more layered aesthetics

7.3 Re-Theming in Figma — Step by Step

  • 1 Duplicate the Semantic Variables collection
  • 2 Create a new Mode named after your brand
  • 3 Remap the six primary color tokens in the new mode
  • 4 Select all frames on your artboards
  • 5 Switch the Semantic collection mode to your new brand mode
  • 6 Every component updates instantly ✓

8. Why This Matters — The Design Engineer Case

Every portfolio reviewer asks the same question: "Why should I care?" This section answers that. Not with claims, but with evidence of how Plinth was built and what it demonstrates about the person who built it.

8.1 Craft

Plinth is the result of hundreds of small correct decisions. Token naming that follows a consistent hierarchy. Layer naming by role, not by appearance — Semantic not Colors. Complete state modelling even for components that could have shipped with just three variants. Three-layer token binding that anticipates future re-theming before a single brand has been built on it.

These decisions are invisible to end users, but they are not invisible to the designers and engineers who will use the system. They feel the difference between a system built to ship features and a system built to be used by other people for years. Craft in design systems is not about pixel-perfect buttons. It is about making the right decision at every layer so that the people downstream never have to undo your work.

8.2 Systems Thinking

The Primitives → Semantic → Component architecture is systems thinking applied to design. It separates concerns, defines clear interfaces between layers, and anticipates future change without over-engineering for hypotheticals. This is the same thinking that makes good software architecture, good organisational design, and good infrastructure engineering.

Plinth demonstrates that the person who built it understands that design systems are not collections of UI components. They are systems — with inputs, outputs, dependencies, and emergent behaviours. Designing a system requires a different mindset than designing a screen. Plinth was built with that mindset from the first token to the last component.

8.3 Career Relevance

Design engineers are rare. Most designers cannot write code. Most engineers cannot design. The intersection is small, and people who operate there are valuable because they translate between two disciplines that traditionally do not speak the same language. Plinth demonstrates both sides: the Figma file shows design rigour — consistent spacing, complete variant coverage, thoughtful token naming. The token JSON file shows engineering literacy — structured data, composable architecture, clear interfaces between layers.

The documentation you are reading right now demonstrates a third skill: the ability to think about how other people will use a system. Writing documentation, naming things well, and designing for adoption are not design skills or engineering skills. They are infrastructure skills. Plinth was built by someone who has them.

NOTEA design system is not a product. It is infrastructure for products. Plinth was built with that distinction in mind from the first token to the last component.
